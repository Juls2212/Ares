# Database Schema

## Scope and migration status

PostgreSQL is mandatory for Ares-owned metadata. Drizzle ORM is used only by Electron Main; renderer and preload never connect to PostgreSQL or receive database credentials. Development uses the local Docker Compose PostgreSQL service described in [DEVELOPMENT.md](DEVELOPMENT.md).

The definitive MVP schema is now defined in TypeScript under `src/main/database/schema/`. No initial migration has been generated, no migration has been applied, and no Ares application table exists in PostgreSQL yet. The next database task must review and generate the initial version-controlled migration. Manual schema changes and `db:push` are prohibited.

## Value constraints and identifiers

Record-oriented tables use PostgreSQL UUID primary keys generated by PostgreSQL through Drizzle's supported UUID default. `settings` uses an internal English `setting_key` as its natural primary key. PostgreSQL table and column names use snake_case; TypeScript properties use camelCase.

Stable domain states use PostgreSQL enums. Cross-column rules and the numeric risk level use check constraints so that their invariants are visible in the migration and enforced by PostgreSQL.

| Enum or constraint | Allowed values or rule |
| --- | --- |
| `task_status` | `PENDING`, `IN_PROGRESS`, `COMPLETED` |
| `task_priority` | `LOW`, `MEDIUM`, `HIGH`; default `MEDIUM` |
| `reminder_status` | `PENDING`, `TRIGGERED`, `CANCELLED` |
| `action_result_status` | `SUCCEEDED`, `CANCELLED`, `VALIDATION_FAILED`, `EXECUTION_FAILED`, `DEPENDENCY_SKIPPED` |
| `application_platform` | `WINDOWS` for the Windows MVP |
| `action_history.risk_level` | `1`, `2`, or `3` |

Action lifecycle states such as `PROPOSED`, `AWAITING_CONFIRMATION`, `APPROVED`, and `RUNNING` are runtime states. They are deliberately not stored as `action_history` terminal results.

## Tables

| Table | Purpose |
| --- | --- |
| `categories` | Optional classifications for planner tasks and events. |
| `tasks` | Work that must be completed, including due-date semantics, priority, and completion state. |
| `events` | Scheduled activities with timezone-aware start and optional end instants. |
| `reminders` | Alerts associated with one task, one event, or an independent subject. |
| `applications` | Known registered applications and validated executable-path references. |
| `application_aliases` | Globally unique, case-insensitive aliases that resolve safely to one registered application. |
| `action_history` | Privacy-aware terminal records of important supervised actions. |
| `settings` | Controlled non-secret preferences keyed by internal English identifiers. |

### Categories, tasks, and events

`categories` has a required bounded non-blank name, optional `#RRGGBB` color, optional internal icon identifier, and timestamps. PostgreSQL rejects empty or whitespace-only names. Its unique index applies `lower(btrim(name))`, preventing duplicate category names that differ only by case or surrounding whitespace. Icon values are identifiers only; arbitrary HTML or SVG markup is not stored.

`tasks` has a required bounded non-blank title, optional description, optional `due_date`, optional `due_time`, priority, status, optional category, optional `completed_at`, and timestamps. PostgreSQL rejects empty or whitespace-only titles. A check constraint prevents a due time without a due date. Another constraint requires `completed_at` for `COMPLETED` and keeps it null for other statuses. The future repository layer must set `updated_at` explicitly; a default does not auto-update it.

`events` has a required bounded non-blank title, optional description, required `start_at`, optional `end_at`, optional category, optional location, and timestamps. PostgreSQL rejects empty or whitespace-only titles. A check constraint requires an end instant to be later than its start. Recurrence and subtasks remain outside the MVP.

### Reminders

Every reminder has a required bounded non-blank `title`, required `remind_at`, delivery status, optional `delivered_at`, timestamps, and optional `task_id` or `event_id`. The title preserves a meaningful subject even when the reminder is independent or an associated record is later removed. PostgreSQL rejects empty or whitespace-only titles.

The `reminders_single_association_check` constraint enforces that `task_id` and `event_id` cannot both be non-null. Thus a reminder is exactly one of the following: associated with one task, associated with one event, or independent. The `reminders_delivery_state_check` constraint requires `delivered_at` only when status is `TRIGGERED`; it must be null for `PENDING` and `CANCELLED`. Service validation must enforce the same association and delivery-state rules and return controlled validation results for invalid input or missing referenced records.

### Known applications and aliases

`applications` stores a bounded non-blank user-visible name, a bounded non-blank executable-path reference, the Windows platform value, favorite/enabled flags, optional `last_launched_at`, and timestamps. PostgreSQL rejects empty or whitespace-only names and paths. Its case-insensitive unique index applies `lower(btrim(executable_path))`, preventing duplicates that differ only by case or surrounding whitespace. Complete Windows path canonicalization remains the responsibility of the future Main-process application registration service. The row contains no command, shell fragment, or argument column. A stored path is never automatically safe: Electron Main must validate it again before a direct launch.

`application_aliases` is a separate table because aliases have no independent meaning and must resolve globally to only one application. It has a required application reference, bounded non-blank alias, and creation timestamp. PostgreSQL rejects empty or whitespace-only aliases. Its unique index applies `lower(btrim(alias))`, preventing aliases that differ only by case or surrounding whitespace from resolving to multiple registrations. The AI resolves an alias to an application ID and never receives an executable path as action input.

### Action history and settings

`action_history` stores a non-blank action correlation identifier, non-blank action name, constrained risk level, terminal result status, bounded non-blank Spanish user summary, optional stable error code, optional safe JSONB metadata, start time, optional finish time, and creation time. PostgreSQL rejects empty or whitespace-only required history text. A check constraint prevents a finish time before its start. It intentionally has no foreign key to mutable domain records so historical entries remain understandable after later changes.

History metadata is optional and must not store credentials, file contents, raw audio, arbitrary prompts, stack traces, or unnecessarily detailed personal content. The future history service decides which safe metadata is recorded.

`settings` stores an internal lower-snake-case English key, JSONB preference value, and timestamps. It may later hold non-secret preferences such as appearance mode, voice-output enabled, wake-word enabled, selected device names, or notification preferences. It must not store plaintext OpenAI credentials, database passwords, captured audio, or other secrets. Future services validate each known key and value.

## Relationships and foreign-key behavior

| Relationship | Cardinality | Delete behavior |
| --- | --- | --- |
| Category to tasks | One-to-many | Deleting a category sets `tasks.category_id` to null. |
| Category to events | One-to-many | Deleting a category sets `events.category_id` to null. |
| Task to reminders | One-to-many, optional from a reminder | Deleting a task sets `reminders.task_id` to null and preserves the reminder. |
| Event to reminders | One-to-many, optional from a reminder | Deleting an event sets `reminders.event_id` to null and preserves the reminder. |
| Application to aliases | One-to-many | Deleting an application cascades only to its aliases, which have no independent meaning. |

Drizzle relations mirror these cardinalities. A reminder's two optional associations are mutually exclusive through the database check and service validation.

## Time and path rules

Exact instants use PostgreSQL `timestamp with time zone`: event starts and ends, reminder times and delivery times, action history times, launch times, completion times, and record timestamps. These values are stored consistently in UTC and converted to the local system zone for Spanish display.

Task due dates use PostgreSQL `date` so they retain their local calendar meaning. A task due time uses PostgreSQL `time` and is valid only with a due date. No exact instant is stored as plain text.

The database stores only application executable-path references. Ares does not store user files, user file contents, wake-word waiting audio, or raw command audio. Paths are normalized and validated in Electron Main before persistence and again before use.

## Indexing intent

- Trimmed, case-insensitive unique lookup for category names, registered executable paths, and application aliases.
- Task status, due-date, and category filtering.
- Event start-time range queries and category filtering.
- Pending reminder scheduling by `remind_at`, plus task and event association lookup.
- Favorite and enabled application filtering.
- Unique action-correlation lookup, history ordering by start time, action-name filtering, and terminal-result filtering.

## Explicit exclusions and deferred work

The schema has no user accounts, authentication, conversation history, personal AI memory, file or file-content tables, recurring-event tables, soft deletion, plugin data, wake-word audio storage, runtime database client, repository layer, database IPC, seed data, or migrations.

The final Windows PostgreSQL provisioning strategy, production credential flow, migration filenames, test-database lifecycle, and any future encrypted credential-reference design remain open decisions. See [OPEN_DECISIONS.md](OPEN_DECISIONS.md).
